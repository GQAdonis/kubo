# Live trigger evals, round 3, 2026-10-12

Rounds 1 and 2 are kept in `results-2026-10-12.md` and `results-2026-10-12-r2.md`.

**Pass bar (operator):** at least 70% of should-trigger prompts (17 of 24) load the expected `ipfs:` skill, and 100% of near-misses stay clean.

**Result: bar MET.** Should-trigger 19/24 (79%), near-misses 8/8 clean. Task 1.4 is ticked.

## What changed since round 2

- No skill description changes this round.
- 22 entry-tool descriptions in `mcp/contract/catalog.json` now end with 'If the <skill> skill is available, load it first ...'.
- The server's initialize `instructions` name all 8 skills and say to load the matching skill before multi-step or confirmation-bearing work (`mcp/server/server.go`). Binary rebuilt with `make build` (version 0.44.0-dev).
- Prompt set unchanged from round 2 (24 positives, 8 near-misses).

## Method

`claude -p <query> --output-format stream-json --verbose --max-turns 2 --allowedTools Skill --disallowedTools Bash`, default model, plugin `ipfs@kubo-ipfs` installed from this repo's marketplace, `ipfs mcp` connected to an isolated offline daemon (API 5181, gateway 8281, no swarm), one run per prompt, empty scratch cwd. Triggered = a `Skill` call naming the expected `ipfs:` skill. Near-miss clean = no `ipfs:` skill called. `claude mcp list` was not run.

**Harness fault and re-run (disclosed):** the first pass ran 4 sessions in parallel. From prompt 4 on, the plugin server showed `failed` at init in every session, because Claude Code wrote `plugin:ipfs:ipfs` into `~/.claude/mcp-needs-auth-cache.json` after a concurrent start failed; those 28 runs had no MCP tools and are discarded (not scored; their cost is included below). I removed only that entry, then re-ran prompts 4 to 31 one at a time; every re-run session showed the server `connected` at init. Prompts 0 to 3 come from the first pass, where the server was connected. Still one scored run per prompt. Total model runs: 60.

**Cost:** about $34.53 for 60 runs (about $15.38 for the 32 scored runs, $19.14 for the 28 discarded).

## Reading the result

- The tool-side pointers and server instructions lifted positives from 54% to 79% with no description change, and near-misses stayed clean (8/8). This confirms the lever was outside the skill descriptions.
- Remaining misses: prompt 3 and 5 (plain CID reads), 11 (a bare `ipns_resolve`), 15 (a bare `dag_stat`) went straight to a one-call tool; prompt 18 loaded `ipfs-pin-management` for a missing `pin_rm` tool, where `ipfs-troubleshooting` was expected (a reasonable adjacent choice, scored as a miss).
- One run per prompt; flips of 2 to 3 prompts between runs are normal (see round 2), so 79% sits above the bar by 2 prompts and should be treated as a pass with little margin.
- Raw stream-json transcripts are not committed (they carry session and path identifiers).
