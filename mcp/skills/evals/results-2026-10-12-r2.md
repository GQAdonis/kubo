# Live trigger evals, round 2, 2026-10-12

Round 1 is kept in `results-2026-10-12.md` (old prompts, old descriptions). This round follows the operator decision of 2026-10-12 for `ipfs-agent-skills` 1.4.

**Pass bar (operator):** at least 70% of should-trigger prompts load the expected `ipfs:` skill, and 100% of near-misses stay clean.

**Result: bar NOT met.** Should-trigger 13/24 (54%), near-misses 8/8 clean. Task 1.4 stays open.

## Method

- Descriptions rewritten to lead with plain user intent (pass A, `skills-ref` valid x8, `check_skills.py` OK 41/41). Prompts rewritten so each positive carries a concrete payload (CID, inline text/JSON, name); 24 positives (3 per skill), 8 near-misses (6 kept, 2 added: SSH key rename for ipns/key tools, Postgres dump for dag/CAR).
- Run A (32 prompts): `claude -p <query> --output-format stream-json --verbose --max-turns 2 --allowedTools Skill --disallowedTools Bash`, default model, plugin `ipfs@kubo-ipfs` installed from this repo's marketplace, `ipfs mcp` connected to an isolated offline daemon (API 5181, gateway 8281, no swarm). One run per prompt, empty scratch cwd, 4 in parallel. Triggered = a `Skill` call naming the expected `ipfs:` skill; near-miss clean = no `ipfs:` skill called.
- One description fix (pass B): the seven skills other than `ipfs-content-search` (which was 3/3) now say 'Invoke this skill first, before calling <tools>' and name what the tool schemas leave out. Re-run B: the 21 prompts of those seven skills plus the 8 near-misses (29 runs). Final per-skill figures use run B for those and run A for `ipfs-content-search`.
- Cost: run A $22.55, run B $11.83, total $34.38 for 61 model runs (the $0.05 to $0.20 runs hit the prompt cache).

## Reading the result

- The description rewrites moved positives from 12/24 (50%) in run A to 13/24 (54%) after pass B. Run-to-run flips in both directions (for example MFS prompt 14 and publish prompt 2) show that one run per prompt carries about +/-3 prompts of noise, so the two passes are not distinguishable.
- Misses are the same behaviour as round 1: the model goes straight to the plugin's MCP tools (`ipfs_add`, `ipfs_cat`, `key_gen`, `dag_stat`) because their own descriptions are enough for a one-call request. Concrete payloads raised the rate from 23% to 50% by themselves; description wording added little on top.
- Near-misses stayed clean in both runs (8/8).
- Not tried, per the budget: a stronger lever is the tool side (for example server `instructions` or tool descriptions that point to the matching skill), which belongs to `mcp/server` and `mcp/contract`; or accepting a lower bar for single-call requests, where the skill adds little because the confirmation flow is enforced by the server anyway.
- Raw stream-json transcripts are not committed (they carry session and path identifiers).
